# Query Projections and Relationship Fetching

| :----------- | :--------- | ---------- | :------- |
| @gabor-boros | 2026-08-12 | 2026-08-15 | accepted |

## Abstract

Elemo stores domain aggregates in Neo4j. Early repository reads hydrated siblings with `OPTIONAL MATCH` plus `collect(DISTINCT ...)` before pagination. That pattern multiplies intermediate planner rows as relation cardinality grows and forced every list or detail response to carry unbounded collections. This ADR records the decision to adopt explicit, typed read projections with root-first pagination, split relation loaders, and cursor-paginated sub-resources for growing relationships, implemented through a small internal query compiler over the official Neo4j Go driver v6 rather than an OGM or general Cypher DSL.

## Decision

### Explicit preload without lazy loading

Transport selects a named use case. The service maps that use case to an allowlisted projection. The repository compiles the projection into a **root query plus optional relation loaders** and executes them in one managed read transaction when response-level consistency matters.

Omitted fields mean "not projected". A loaded to-one that is absent is `null`. A loaded to-many that is empty is `[]`. Partial collections always carry page metadata. Repository persistence structs are not serialized directly as HTTP DTOs.

### Root-first pagination and bounded relations

List reads page root nodes first using a fully unique order on `id` (XID is k-sortable) and opaque cursor tokens (`page_size+1`, `next_page_token` / `has_more`). Stored `created_at` is a display property and is not recovered from the id. Bounded to-one relations may be joined on the root query. Sibling to-many relations are loaded with `UNWIND $ids` batch queries, one loader per selected relation. Counts use `COUNT { ... }`. Bounded `COLLECT { ... ORDER BY ... LIMIT ... }` subqueries are reserved for deliberate previews, not mandatory aggregates. Remaining `collect(DISTINCT ...)` usage is confined to those UNWIND loaders, not pre-pagination sibling expansion.

### Cardinality rule

Growing or high-cardinality to-many relations are **not** embedded as unbounded `Partial*` arrays on parent list or detail responses. They are exposed as counts on the parent and/or dedicated cursor-paginated sub-resources:

| Parent | Growing relation | Parent field | Dedicated page |
| :----- | :--------------- | :----------- | :------------- |
| Project | issues | `issue_count` | `GET /v1/projects/{id}/issues` |
| Project | documents | `document_count` | `GET /v1/projects/{id}/documents` |
| Namespace | projects | `project_count` | `GET /v1/namespaces/{id}/projects` |
| Namespace | documents | `document_count` | `GET /v1/namespaces/{id}/documents` |
| Organization | members | `member_count` | `GET /v1/organizations/{id}/members` |
| Organization | namespaces | `namespace_count` | `GET /v1/organizations/{id}/namespaces` |
| Role | members | `member_count` | `GET /v1/organizations/{id}/roles/{role_id}/members` |
| User | documents | `document_count` | not listed on the user resource |
| Document | comments, attachments | `comment_count`, `attachment_count` | comment/attachment `ListBelongsTo` (HTTP pages not yet exposed) |
| Issue | comments, attachments, watchers, relations | `*_count` | dedicated sub-resources as needed |

Bounded low-cardinality to-one or small to-many relations may be inlined when explicitly projected.

Domain aggregates in `internal/model` validate the entity itself. They do not hold growing or high-cardinality relation ID lists, and they do not carry relation counts. Counts belong on repository and HTTP read models; traversal uses dedicated cursor pages. Bounded to-one or small to-many fields may stay on the aggregate when they are part of the entity (for example `Issue.Assignees`, `Document`/`Issue` labels, `Issue.Links`, `Issue.Parent`).

### Internal query compiler

Cypher structure is compiled from closed Go types (`ProjectProjection`, `IssueListQuery`, `CursorPage`, `SortDirection`, and similar). Callers never pass raw Cypher fragments from HTTP. Compiled statements are named and fingerprinted for cache keys and observability without embedding parameter values.

The official Neo4j Go driver v6 remains the production foundation. The compiler wraps driver sessions and managed transactions; it does not replace the driver. Typed record decoding prefers Neo4j generic getters over JSON round-trips as each read model migrates.

### Layer ownership

- **Transport / OpenAPI:** parse named views and cursor parameters; publish summary, detail, and page schemas.
- **Service:** choose allowed projections, enforce authorization and include limits, and compose read models.
- **Domain (`internal/model`):** validate the entity; do not hydrate graphs or store growing relation ID slices.
- **Repository:** own Cypher, root-first pagination, batching, transaction consistency, and decoding.
- **Cache:** key by canonical query specification, projection, filters, order, and cursor. Prefer caching bounded pages and summaries. Get invalidation uses `DeletePattern` over `Get:{id}:*` so every projection variant is cleared.

PostgreSQL and S3 list methods reuse the shared `CursorPage` / `Page[T]` contract where applicable. They do not route through the Cypher compiler.

### Rejected alternatives

- **Mandatory embedded aggregates on every Project/Issue response:** improves convenience for small demos but does not scale with relation degree.
- **OGM or automatic lazy loading:** hides query cost, invites N+1 patterns, and couples domain models to persistence graphs.
- **Third-party Cypher builders that accept arbitrary fragments:** weaken parameter safety and plan-cache stability compared with closed allowlisted compilers.
- **Offset-only pagination for Neo4j lists:** unstable under concurrent inserts for the access patterns Elemo needs; cursor continuation on `id` is the default for graph lists.

## Consequences

### Positive

- Read cost scales with selected projection and page size rather than total relation degree.
- Sibling to-many relations no longer cross-multiply before aggregation.
- OpenAPI contracts make omitted, null, empty, and partial collection states explicit.
- Cache entries stay small and invalidate around relation-specific pages.
- A single internal model covers Neo4j reads and shared page metadata for other stores.

### Negative / trade-offs

- Call sites must choose projections and page tokens instead of receiving fully hydrated aggregates.

### Risks

- Incorrect projection defaults can under-fetch UI fields. Mitigate with named list/detail helpers and transport/service tests for response semantics.
- Cursor tokens encode continuation state; malformed tokens must fail closed as invalid input.
