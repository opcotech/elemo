# Scoped Relationship-Based Authorization

| author       | created at | updated at | status   |
|:-------------|:-----------|------------|:---------|
| @gabor-boros | 2026-08-19 | -          | accepted |

## Abstract

Authorization in Elemo is scoped relationship-based access control (ReBAC). A
check succeeds only when an actor can reach a **principal**, that principal
holds a **GRANTED** edge on a **scope**, the requested resource is that scope
or lies on an **IN_SCOPE_OF** path to it, and the grant's actions (or the
referenced role's actions) contain the requested action by **exact string
match**. There are no system roles, no ResourceType permission bindings, and
no wildcard action (`*`).

This ADR supersedes the authorization model in
[Authentication and Authorization] and the permission-kind model in
[Front-end Permission Handling]. Authentication (OAuth2, Redis sessions)
described in the former still applies.

[Authentication and Authorization]: 0010.authentication-and-authorization.md
[Front-end Permission Handling]: 0018.front-end-permission-handling.md

## Decision

### Principals

Only `User`, `Team`, and `Organization` nodes are principals. They carry the
`Principal` label. A grant's source must be one of these types.

Evaluation walks `MEMBER_OF` **zero or one** hop from the actor:

* `0` — the actor is the principal (a user granting themselves, or an
  organization/team used as principal directly)
* `1` — the actor is a member of a team or organization that holds the grant

Inactive users (`status` other than `active`) are ignored as actor and as
principal.

`Installation` is not a principal, not an organization, has no members, and
has no `IN_SCOPE_OF` children.

### Scopes and `IN_SCOPE_OF`

Domain edges (`HAS_NAMESPACE`, `HAS_PROJECT`, `BELONGS_TO`, `SCOPED_TO`,
`HAS_TEAM`, …) stay as the product graph. Authorization additionally requires
an explicit `IN_SCOPE_OF` chain:

* `Issue` → `Project` → `Namespace` → `Organization`
* `Document` / `Folder` → library (typically the namespace)
* `Todo` → owner `User` (graph consistency only; access is owner identity, not `GRANTED`)
* `Comment` → parent issue or document
* `Team` → owning organization or project

`IN_SCOPE_OF` must not form a cycle. A resource is in scope of itself
(zero-length path) and of every ancestor along that chain.

### Grants

A `GRANTED` relationship is the only source of authority for organization-scoped
resources. Personal todos are authorized by owner identity (`ctx` user equals
`OwnedBy`), not a grant.

```
(principal:Principal)-[:GRANTED {id, role_id?, actions}]->(scope)
```

* `actions` is a list of fine-grained action strings (see `internal/model/action.go`)
* `role_id`, when set, names a `Role` node whose `actions` list is unioned
  with the grant's own `actions`
* A role has **no intrinsic authority**. Copying a template onto an
  organization (`DEFINES_ROLE`) does nothing until a `GRANTED` edge points at
  a scope and references that role

Action match is exact. `organization.read` does not imply
`organization.update`. There is no `*`, no `create`/`read`/`write` kind
hierarchy, and no ResourceType-level binding.

`organization.create` is granted only on the `Installation` node
(`id: 00000000000000000000`). It is never included in role templates and is
never implied by organization membership.

### Installation

Bootstrap creates a singleton `Installation` with the stable nil xid:

```
MERGE (i:Installation {id: '00000000000000000000'})
ON CREATE SET i.created_at = datetime()
```

Bootstrap attaches **no grants** to it. The ability to create organizations
is an explicit `GRANTED` from a user principal onto Installation, with
`actions = ['organization.create']` only.

### Roles

System roles `Owner` / `Admin` / `Support` are removed. Each organization
receives a copy of the inspectable templates in `model.RoleTemplates`:

| key                   | purpose                                      |
|:----------------------|:---------------------------------------------|
| `org-admin`           | Full authority inside the org, excluding `organization.create` |
| `org-member`          | `organization.read`                          |
| `namespace-admin`     | Administer a namespace and descendants       |
| `project-maintainer`  | Maintain a project, its issues and documents |
| `project-viewer`      | `project.read`, `issue.read`, `document.read` |
| `issue-maintainer`    | Update and assign an issue                   |
| `document-maintainer` | Update a document or folder                  |

Personal todos are not grantable org capabilities. Any authenticated user may
create, list, update, and delete todos they own (`ctx` user equals `OwnedBy`).
`IN_SCOPE_OF` from a todo to its owner remains for graph consistency.

Typical intra-org wiring:

* Creator receives `org-admin` on the organization
* The organization principal receives `org-member` **on itself**, so every
  `MEMBER_OF` the org can `organization.read` without a per-user grant

Cross-org collaboration is a `GRANTED` from a foreign principal (user, team,
or the other organization) onto a resource in this org — for example Nova
Labs `project-viewer` on ACME's PLAT project — without `MEMBER_OF` the target
org.

Teams are principals, not roles. `HAS_TEAM` is structural ownership
(org/project owns a team). Team membership is `MEMBER_OF`. Team authority is
a `GRANTED` from the team onto a scope.

### Listing and opening resources

`ReadActionFor` names the action that authorizes a resource type (`project.read`
for a project, `issue.read` for an issue, and so on). Grants still inherit
**down** `IN_SCOPE_OF` only: a `project-viewer` grant on a project does not
confer `namespace.read` on the parent namespace.

* **GET a resource** requires that resource's read action on it (or an
  ancestor).
* **List children of a parent** does **not** require the parent's read action.
  Each row is included only when the actor has the **child's** read action.
  An unknown or empty parent yields an empty page, not `403`.
* A **namespace is reachable** (appears in workspace discovery and may be used
  as a route shell) when the actor has `namespace.read` on it **or** can read
  at least one descendant (`project.read`, `issue.read`, or `document.read`).
  Reachability is not `namespace.read`: documents, members, and settings on
  that namespace still require the namespace's own actions.
* **Parent GET / update / admin** still require the parent's own actions.

The UI must not require parent `.read` to open a child the actor can already
GET. Operational namespace and project routes use reachability and the child's
read action. Organization and namespace **settings** still require
`organization.read` / `namespace.read`.

### Front-end checks

The `/v1/permissions/resources/{id}` endpoint returns the actor's
**effective actions** on that resource. UI helpers must test those exact
action strings (for example `project.update`). They must not treat `*` as
allow-all, and they must not infer `read` from `write`.

SSR loaders and `usePermissions` remain valid; only the meaning of a
"permission" changes from a coarse kind to an action.

### Rejected alternatives

* **System roles bound to ResourceType** (`HAS_PERMISSION` with `*` /
  `create` / `read` / `write`): global superuser semantics that leak across
  orgs and private resources (todos).
* **Wildcard `*`**: hides the action set and cannot be audited per capability.
* **OPA / external policy engines**: extra operational complexity for a graph
  already able to express ReBAC.
* **Membership alone as access**: `MEMBER_OF` an org does not grant project
  or issue actions; those require an explicit `GRANTED` on a scope that
  reaches the resource via `IN_SCOPE_OF`.

## Consequences

Authorization is local to a scope and auditable as a small set of `GRANTED`
edges. Creating an organization does not confer the right to create further
organizations. Partner access is a grant, not dual membership.

Call sites and the front end must name exact actions. Seed data and tests
must materialize `IN_SCOPE_OF` alongside domain edges; missing scope links
deny access even when a grant exists on an ancestor. Listing and navigation
must use the child's read action (or namespace reachability), not a parent
`.read` gate, so a `project-viewer` grant can open that project without
`namespace.read`.
