# Typed Custom Fields

## Abstract

Custom fields extend Elemo resources with additional typed attributes. They
are not a substitute for the product graph: core relationships stay first-class
graph edges, and plugins must not smuggle domain models into unstructured
JSON. Definitions, type-specific schemas, options, and values live in
PostgreSQL. Neo4j remains authoritative for resource existence, `IN_SCOPE_OF`
ancestry, typed references, and ReBAC. There is no `draft`/`active`/`archived`
state machine. A created definition is immediately usable; identity is
immutable; schema evolution is constrained in place; a boolean `archived` flag
retires a field without destroying stored values.

## Decision

### Storage boundary

PostgreSQL owns:

* custom-field definitions (key, name, description, kind, scope, target type,
  required, archived, index capabilities, owner user, OAuth registrar client)
* type-specific schema tables
* stable select options
* atomic typed values (one representation per row)
* durable cross-store operation records for hybrid create/delete

Neo4j owns:

* target resource existence
* `IN_SCOPE_OF` ancestry used to resolve inherited definitions
* existence of `user_reference` and `resource_reference` targets
* ReBAC (`GRANTED` / `IN_SCOPE_OF`)

PostgreSQL never infers graph ancestry. Neo4j never stores custom-field
payloads. Definition and value state is not duplicated across stores.

### Type system

Kinds are a closed set: `text`, `integer`, `decimal`, `boolean`, `date`,
`datetime`, `url`, `single_select`, `multi_select`, `user_reference`,
`resource_reference`. Each kind has only its relevant constraints and a typed
value shape. There is no `map[string]any` in the domain or API, and no
JSON/JSONB schema or value column.

Decimal values are stored as `NUMERIC`. Dates use `DATE`; datetimes use
`TIMESTAMPTZ`. Multi-valued kinds (`multi_select`, and reference kinds with
`multiple`) store one atomic row per element with an ordinal.

### Identity, evolution, and retirement

A created definition is immediately usable. Identity is frozen from insert:
stable `key`, kind, scope, owner, target resource type, and registrar client.
Display name, description, and display order may change. Select options may be
added or disabled; an option key is never reused or deleted while referenced. Index
flags may change only to capabilities the kind allows. `required` is enforced
on Issue create (via staged writes) and on later writes of that field for any
target type; it is not a backfill gate over existing resources. Staging on
create is currently wired for issues only.

`archived` is a boolean, not a workflow state. Archived fields are omitted
from effective lists and issue surfaces (even when stored values exist),
disappear from create/edit, and reject new writes. Stored rows remain in
PostgreSQL so hard delete is still blocked while values exist.

### Scope and inheritance

A definition is scoped to an organization, namespace, or project and applies
to one target resource type. Effective fields for a resource are the
non-archived definitions whose scope is the resource itself or an
`IN_SCOPE_OF` ancestor, matching the target type. Local project definitions
are editable at the project; inherited definitions are visible with their
source scope. Effective and settings lists show ancestor scopes first
(organization, then namespace, then project), then `order` within each scope.
Inherited fields keep the display order from their source scope.

### Authorization, license, and provenance

Definition mutation requires `custom_field.manage` on the definition's scope
(organization-admin, namespace-admin, and project-maintainer templates).
Reading values uses the target resource's existing read action; writing values
uses its existing update action.

Writes are gated by `license.FeatureCustomFields`. The license model exposes
only the boolean feature, not a custom-field quota.

OAuth clients act on behalf of a user. Each definition records the owner user
ID and the registrar client ID from the same token. There is no Plugin
resource type.

### Cross-store orchestration

Issue create with initial custom-field values preallocates the issue ID,
stages uncommitted value rows plus a pending operation in PostgreSQL, creates
the Issue in Neo4j idempotently with that ID, then commits the staged rows.
Failures compensate immediately. A worker reconciles stale pending operations:
if the graph resource exists, values are committed; otherwise uncommitted
rows are removed. Resource deletion issues an idempotent PostgreSQL
`DeleteForResource`. Reads always verify graph existence and authorization
first, so crash-created orphans cannot be exposed.

### HTTP contract

The REST surface is generic (`/v1/custom-fields` for definitions,
`/v1/resources/{resource_type}/{id}/custom-fields` for values). Issue create
may include typed initial entries. Core resource responses do not embed
custom-field maps. OpenAPI uses discriminators, closed enums, and
`additionalProperties: false`.

## Consequences

* Custom fields can use PostgreSQL constraints, exact numeric types, and
  partial indexes that Community Neo4j cannot express.
* Hybrid writes are explicitly orchestrated; the system does not claim
  cross-store atomicity.
* Adding a kind requires a schema table (or columns), domain validation,
  OpenAPI members, and UI controls together.
* Existing organizations receive `custom_field.manage` only on newly copied
  role templates; operators must grant the action on existing roles if needed.
