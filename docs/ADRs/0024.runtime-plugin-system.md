# Runtime Plugin System

| author       | created at | updated at | status   |
|:-------------|:-----------|------------|:---------|
| @gabor-boros | 2026-08-30 | 2026-08-31 | accepted |

## Abstract

Elemo needs third-party and first-party extensions that install, enable, and
disable at runtime without restarting the process. This ADR records the
production plugin platform: a WASM backend runtime behind an Elemo interface,
client-only ESM frontend modules loaded through import maps (not Module
Federation), PostgreSQL for install and activation state, a host-mediated
Neo4j graph so plugins can declare nodes and relations, and a capability-
checked Plugin API. Plugin domain models are first-class graph nodes
(`Extension`), not JSON bags on core entities. Authorization stays scoped
ReBAC with a single new resource type and four extension actions.

## Decision

### Composition and process model

The plugin platform is constructed in the Cobra composition root with
manual constructor injection, the same as every other service. Runtime
plugins are not Uber Fx modules and do not mutate a DI graph. Go
`plugin.Open` is not used.

Installation is instance-wide (package files plus `plugin_installations`).
Activation is scoped (organization, namespace, or project) via
`plugin_activations`. Installed does not mean enabled. On server start the
registry restores installed plugins and starts those with at least one
enabled activation. That is crash-recovery, not “install requires restart.”

### Backend runtime

Guest code runs as WASM. The host depends only on:

```go
type Runtime interface {
    Load(ctx context.Context, plugin Plugin) error
    Start(ctx context.Context, pluginID string) error
    Stop(ctx context.Context, pluginID string) error
    Call(ctx context.Context, pluginID, function string, input []byte) ([]byte, error)
}
```

**Extism was evaluated and not used as the guest ABI.** Extism’s Go PDK
targets TinyGo and the Extism-specific import module. The reference plugin
and public SDK compile with `GOOS=wasip1 GOARCH=wasm -buildmode=c-shared` on
Go 1.26, which produces a WASI reactor (`_initialize`) that exports
`//go:wasmexport` functions and imports a first-party `elemo` host module.
Extism `Call` cannot invoke those exports without the PDK ABI.

The production implementation is **wazero** (WASI preview 1) behind the
same `Runtime` interface. Timeouts come from config and honor context
cancel. WASM traps are recovered and returned as structured errors; the
host process never panics. Guests receive no filesystem, network,
environment, or database host functions. The in-memory registry is
concurrency-safe and does not hold its lock during `Call`.

Disable and upgrade stop routing new work, wait in-flight with a timeout,
swap the snapshot, and deactivate the old version. Plugin SQL migrations
are out of v1; JSONB `plugin_storage` is enough for private non-graph data.

### Frontend loading

The web app is TanStack Start + Vite. Module Federation is not used.
Frontend plugins load as **client-only ESM** via `import()`, with React and
the plugin SDK/UI shared through an import map so plugins do not ship a
second React. Plugin JSON APIs go through the existing BFF. Asset GET
URLs are same-origin proxies so `import()` does not send a bearer token to
the Go API.

Frontend plugins run in the Elemo origin with full page privileges. v1
allows only administrator-installed packages. Iframe sandbox is a later
extension point.

### Persistence boundary

PostgreSQL owns:

* `plugin_installations` (id, plugin_id, version, status, manifest JSONB)
* `plugin_activations` (plugin_id, scope_id, enabled, config JSONB)
* `plugin_storage` (plugin_id, scope_id, key, value JSONB)

Neo4j owns plugin domain graphs. Plugins never receive Neo4j credentials,
never submit Cypher, and never mutate core labels or authz edges
(`IN_SCOPE_OF`, `GRANTED`, `MEMBER_OF`, `DEFINES_ROLE`).

### Plugin-defined graph

A single closed resource type `ResourceTypeExtension` (label `Extension`)
holds every plugin node. Discriminators are properties, not new enum
values: `plugin_id`, `kind`, declared scalars, `created_at` /
`updated_at`. `Has()` already matches `resource.Label()`, so org grants
that include `extension.read` apply once `IN_SCOPE_OF` is in place.

Manifest `graph` declares nodes, relations, and optional `foreign` aliases.
Validation at install rejects unknown property types, reserved property
names, cycles in `scope.parent`, collisions with core `EdgeKind` names,
and foreign names that collide with core types or local kinds. Foreign
aliases are a declared shape (parent + properties) only; they are bound
to another installed plugin’s kind at **activation** via a
`graph_binding` config field. Relation Neo4j types stay owned by the
**declaring** plugin (`EXT__{plugin}__{KIND}`). `CreateRelation`
validates `from`/`to` against local kinds, core types, or a resolved
foreign binding, and enforces declared cardinality (409 on conflict).
`ListRelations` accepts `direction=outgoing|incoming|both`.

Cross-plugin **reads** (`graph.nodes.get` / `list` with `owner_plugin_id`)
are allowed only when the caller has a resolved binding for that
owner+kind, `graph.read`, both plugins active on the scope, and
`extension.read`.

Activation config is declared on the manifest (`string`, `integer`,
`boolean`, `graph_binding`) and stored on `plugin_activations.config`.
WASM guests read the nearest enabled ancestor via `plugin.config.get`
without `plugin.storage.read`. HTTP GET/PATCH `/v1/plugins/{id}/config`
requires `plugin.manage` on the exact scope.

The host always writes `IN_SCOPE_OF` from `scope.parent`. Domain edges are
namespaced `EXT__{pluginIdSanitized}__{KIND}` so they never collide with
core kinds. Rel types are interpolated only after an allowlist check.

Create always: validate against the plugin schema, allocate an Extension
xid, write the node, write `IN_SCOPE_OF` to the parent, optionally write a
declared domain relation in the same transaction.

Disable leaves graph rows in place and returns 404/forbidden until
re-enabled. Uninstall deletes all `Extension` nodes with that `plugin_id`
and all `EXT__{plugin}__*` relationships, including edges from core nodes.
That is destructive. Schema upgrades are additive-only in v1.

JSONB `plugin_storage` remains for private non-graph blobs.

### Authorization

ReBAC actions:

* `plugin.install` — upload, upgrade, uninstall. Not on org role templates.
  Granted on the Installation node (same pattern as `organization.create`).
* `plugin.manage` — enable/disable at org/namespace/project. On org-admin,
  namespace-admin, and project-maintainer.
* `extension.create` / `extension.read` / `extension.update` /
  `extension.delete` — user ReBAC on plugin graph nodes. The four strings
  are exact; per-kind plugin actions are deferred. `extension.read` is also
  on project-viewer and the organization-member role template. Relating
  *to* a declaring plugin’s own kind requires `extension.read` on the
  target (so project maintainers can attach time to an org-scoped Budget).
  Relating *from* a foreign node still requires update on that node.

Plugin **capabilities** (`issues.read`, `graph.write`,
`plugin.storage.write`, …) are a closed set separate from ReBAC. Every
host call requires capability AND user/request ReBAC. Installing a plugin
does not grant it implicit power. Graph host calls additionally require
`graph.read` or `graph.write`.

License feature: `FeaturePlugins`. It is in `DefaultFeatures` so existing
test licenses work.

### Events

There is no Redis/NATS/WebSocket event bus in v1. An in-process publisher
(`internal/pkg/event`) is used. Domain services emit into it; plugin
handlers subscribe dynamically. Frontend hot-activation is React Query
refetch after admin mutations plus `refetchOnWindowFocus`. The publisher
is shaped so realtime invalidation can be added later.

Events in v1: `issue.created`, `issue.updated`, `issue.deleted`,
`project.created`, `project.updated`, `extension.created`,
`extension.updated`, `extension.deleted`. Extension events are
dispatched to active plugins that listed them; plugins with
`graph.foreign` only receive another plugin’s extension events when
`plugin_id`+`kind` match a resolved binding (or the event is their own).
Publish must not fail CRUD. Plugin handler failure is logged; one attempt
with timeout, no retry storm.

### HTTP

Plugin JSON APIs live under `/v1` (OpenAPI + chi + oapi-codegen strict
handlers). Plugin **assets** are a manual chi route with auth, safepath,
content types, and cache headers. Disabled plugins cannot fetch assets.

`POST /v1/plugins/{pluginId}/invoke` exists regardless of installed
plugins. Disabled or missing plugins return 404.

### Out of v1

Process plugins, marketplace, OCI, signatures, iframe sandbox, plugin
SQL/Cypher migrations, plugin-to-plugin install dependencies, background
plugin workers, SSR of plugin UI, WebSocket registry push, Meilisearch
for `Extension` nodes, custom-field references to plugin kinds, per-kind
ReBAC actions.

## Consequences

* Plugins can ship domain graphs (for example Account/Budget or TimeEntry)
  that the rest of Elemo may relate to, without opening `ResourceType` or
  `EdgeKind` at runtime.
* Uninstall is destructive for that plugin’s graph. Operators must be
  warned in the admin UI and developer guide.
* Frontend plugins are fully privileged in the origin. Only admins may
  install packages in v1.
* The wazero ABI is Elemo-specific. A later Extism adapter can implement
  the same `Runtime` interface if TinyGo PDK guests become a requirement.
* Additive-only schema upgrades mean removing a kind or required property
  requires a future migration story.
